# Git 提交规范

## 一、不主动提交（硬性要求）

- **默认只改代码，不执行 `git commit`。** 即使任务看起来已经完成，也不要顺手提交。
- 完成改动后可以**提醒**用户，例如：「改动已完成并通过测试，需要我提交吗？」
- 只有用户明确说出「提交」「commit」「帮我提交」之类的指令时才提交；用户只是询问状态、审查改动时不算授权。
- 未经明确要求，不执行 `git push`、`git tag`、`git reset --hard`、`git rebase`，也不改写已有提交（`--amend`、force push）。
- 提交前先看 `git status` 和 `git diff`：只暂存本次任务相关的文件，不要把用户未完成的工作、生成物或无关文件一起带上；不确定时先问。

## 二、标签（type）

格式固定为：

```text
<type>: <subject>
```

可用标签：

| 标签 | 用途 | 示例 |
|---|---|---|
| `feat` | 新增功能或能力 | `feat: add YAML format support` |
| `fix` | 修复缺陷 | `fix: reject empty keys in dotenv parser` |
| `docs` | 只改文档、注释 | `docs: document layered merge rules` |
| `refactor` | 重构，不改变外部行为 | `refactor: split format packages from sources` |
| `test` | 只改测试 | `test: cover overflow errors for Int extraction` |
| `ci` | CI、构建流水线 | `ci: run tests on all targets` |
| `chore` | 杂项、依赖、版本号 | `chore: bump version to 0.1.4` |

规则：

- 一次提交只做一件事；跨类别的改动拆成多个提交。
- 拿不准时选最贴近的标签；纯版本号、依赖、脚手架用 `chore`。
- 需要范围时写成 `<type>(<scope>): <subject>`，scope 用小写，例如 `fix(json): ...`。
- 破坏性变更在标签后加 `!`，例如 `feat!: rename Source::collect to Source::load`，并在正文说明迁移方式。

## 三、内容是英文

- `subject` 和正文**一律用英文**，不要中英混写。
- `subject` 用祈使句、小写开头、结尾不加句号，尽量控制在 72 字符以内。
- 写「做了什么、为什么」，不要写「修改了文件」这类无信息量的描述。
- 正文与 `subject` 之间空一行；需要时用 `-` 列要点，解释动机、影响范围和迁移方式。
- 不写「Generated by AI」之类的署名，也不要把密钥、token、内网地址写进 message。

推荐：

```text
fix: reject empty keys in dotenv parser

Empty keys previously produced a table entry with an empty name, which
broke path lookup. Report the line number instead.
```

避免：

```text
update code                # 没有信息量
修复了一些问题              # 不是英文
feat: Added new feature.   # 过去式、大写开头、多余句号
```

## 四、提交前检查

- 代码类改动按项目规范跑：`moon info && moon fmt`，再跑 `moon check`、`moon test`；改到输出时用 `moon test --update` 刷新快照。
- 确认 `.mbti` 的 diff 符合预期，没有把生成物、`_build/` 或临时文件加入暂存区。
- 只提交与本次任务相关的文件；用户未要求时不要提交其工作区里的其他修改。
- 提交后报告：提交哈希、message、包含的文件范围，以及测试结果。
