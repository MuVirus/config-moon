# moonfig 文档撰写规范

文档的定位是“原则指引”与“名词解释”，不是代码的镜像。阅读任何文档时，读者应当能比直接翻阅代码更快、更准地理解意图。

编写任何文字前，先问自己：**读者直接看代码是否更快？** 如果是，请使用链接指路，绝不要复制粘贴。

## 一、必须保留的内容（Keep）

- **底层逻辑（The WHY）**：某个设计存在的原因，以及文件分类背后的原则。
- **跨平台架构约束**：文档必须显性说明核心逻辑跨平台，并解释外围适配为何隔离在非核心独立 package 中。
- **非显而易见的发现**：平台的怪异行为、隐蔽的约束，例如“如果删掉 X，就会导致 Y 崩坏”。
- **指路牌（Pointers）**：说明东西放在哪里，包含什么类型的文件，以及归属规则。

## 二、必须丢弃的内容（Shed）

- **代码的复读机**：具体的类名、文件清单、枚举值、命令行矩阵。
- **流水账与更新日志**：例如“我们重命名了 X”、“Y 被移除了”，或者尝试过但废弃的方案。
- **精确统计值**：具体的数量、行号等一切通过阅读代码就能知道的信息。
- **废话连篇的叙事**：一句话能通过给一个链接解决的，就把它变成链接，不保留文字。

## 三、链接与单一事实来源（核心红线）

- **单一事实来源（One home per fact）**：每个事实只能有一个权威存放地。其他文档需要引用时，必须使用**可点击的 Markdown 链接**指向该位置，禁止复制粘贴。
- **向下导航**：文档呈树状结构，通过链接向下延伸。根节点链接子文档，子文档链接具体模块。
- **严禁方位词**：引用其他内容时，严禁使用“下面”、“如上所述”、“详见小节 3”等指代方位的词汇，除非紧邻下一行就是该内容。

## 四、moonfig 项目专属约束

- **架构隔离**：核心逻辑必须跨平台；外围适配（IO、环境变量、FFI）隔离在独立 package，且不保证跨平台通用性。术语统一：包用 `package`，模块用 `module`，不混用“子包”。
- **代码与注释规范**：代码块必须标语言。文档注释里的示例用 `mbt check`（随 `moon test` 跑）；README 里的片段用 `moonbit nocheck`；说明性片段用 `moonbit`、`sh`、`text` 等。展示功能必须给实际例子，禁止只罗列 API。公开 API 必须有 `///` 注释（防 `E0074`），必须说明边界与异常。

## 五、落笔与校验

- 成对的文档要同步改：`README.mbt.md` ↔ `README_EN.md`，`AGENTS.md` ↔ `AGENTS_ZH.md`。
- 链接用相对路径：`docs/design/` 与 `docs/plan/` 之间写成 `../design/design.md`。
- 结论先行：先给规则，再给理由；实测数据写明来源。
- 不复制 `moon doc` 已经能生成的 API 清单，也不写和代码无关的客套话。
- 标 `mbt check` 的代码块会被 `moon check` / `moon test` 校验，改完跑一遍。
- 移动或重命名文档后，搜一遍全仓库的旧路径引用。

## 六、审查与精简（Edit Pass）

审查文档时，一旦发现以下情况，直接删除：

- 枚举了代码中已有的信息。
- 废话连篇的叙事。
- 复制粘贴了其他文档已有的事实。

如果一句话能通过给一个链接解决，就把它变成链接，不要保留文字。
