# moonconfig 文档撰写规范

文档的定位是“原则指引”与“名词解释”，不是代码的镜像。阅读任何文档时，读者应当能比直接翻阅代码更快、更准地理解意图。

编写任何文字前，先问自己：**读者直接看代码是否更快？** 如果是，请使用链接指路，绝不要复制粘贴。

## 一、 必须保留的内容（Keep）
- **底层逻辑（The WHY）**：某个设计存在的原因，以及文件分类背后的原则。
- **跨平台架构约束**：必须显性说明核心逻辑是跨平台的。解释为何为兼容无 IO/环境变量的平台，必须将此类操作隔离在非核心的独立子包中。
- **非显而易见的发现**：平台的怪异行为、隐蔽的约束，例如“如果删掉 X，就会导致 Y 崩坏”。
- **指路牌（Pointers）**：说明东西放在哪里，包含什么类型的文件，以及归属规则。

## 二、 必须丢弃的内容（Shed）
- **代码的复读机**：具体的类名、文件清单、枚举值、命令行矩阵。
- **流水账与更新日志**：例如“我们重命名了 X”、“Y 被移除了”，或者尝试过但废弃的方案。
- **精确统计值**：具体的数量、行号等一切通过阅读代码就能知道的信息。

## 三、 链接与单一事实来源（核心红线）
- **单一事实来源**：每个事实只能有一个权威存放地（One home per fact）。其他文档需要引用时，必须使用**可点击的 Markdown 链接**指向该位置，绝禁止复制粘贴。
- **向下导航**：文档呈树状结构，通过链接向下延伸。根节点链接子文档，子文档链接具体模块。
- **严禁方位词**：引用其他内容时，**严禁使用**“下面”、“如上所述”、“详见小节 3”等指代方位的词汇（除非下一行就是该内容）。

## 四、 moonconfig 项目专属约束
- **核心与非核心隔离**：文档中必须明确区分核心逻辑（跨平台）与外围适配（如文件读取、环境变量、未来的 FFI 扩展）。说明外围模块依赖底层系统，不保证跨平台通用性。
- **踩坑点必须显性化**：涉及“JSON 整数转 `Int64` 精度丢失”、“Int64 序列化需转字符串”、“数组完全替换”等隐蔽逻辑时，必须在文档中说明。
- **代码示例规范**：代码块必须标明语言（如 ```moonbit）。展示功能时，必须给出实际使用的例子，禁止只罗列 API。

## 五、 审查与精简（Edit Pass）
审查文档时，一旦发现以下情况，直接删除：
- 枚举了代码中已有的信息。
- 废话连篇的叙事。
如果一句话能通过给一个链接解决，就把它变成链接，不要保留文字。
